Since 2025, I've been using this blog as a sandbox to experiment with AI/LLM-assisted development. These are my mistakes, my learnings, and my takeaways, from scratch to shipped.

Disclaimer: I am neither affiliated with Cursor nor Anthropic, just a customer. Use LLMs on your projects at your own risk.

**1. Overcoming Friction**: Prior to 2025, this blog sat like many side projects in a somewhat embarrassing, half-baked state. It was never a top priority and I was never comfortable with editing CSS/HTML/liquid. When I first started with Cursor, the early days of use were a mix of novelty and frustration, and the code drifted into a bit of a mess.

Why didn't I keep at it? Looking back, I found that I ended up having to steer cursor hard, in CSS that I didn't understand well, and it gave me the feeling of pulling a slot machine to get changes going.

**2. Overcoming Breakages**: At the end of 2025, like many others, I sat down with a Claude subscription over the holidays and gave this a try again. I also came into this with a couple of clear ideas including red-green-refactor loops that I wanted to test and build into my workflow.

From working with other codebases and getting to grips with my first compiled languages, I found myself wanting a fast feedback loop for what was breaking / regressing. I wanted the test suite to be something I could read and tinker with, opting for a language that I know well (python) with standard and friendly tooling (playwright, pytest, uv).

I'm more than happy with the results so far, and I got a few more things than I planned out of the system.

The first, and most obvious one, was that each automated test means something I didn't have to check manually, and this let me attack bugs with more detail and focus. When I was naively prompting Cursor, I found the CSS changes to be quite fragile (e.g. unexpected colour changes), and having test output that I could throw back into a session allowed the LLM to self-diagnose the issues, leaving me free to think about the next thing that I wanted fixed.

The second benefit was that the structure of tests and the diagnosis of the problem gave me a little peek into how browsers work. One early annoyance as I pushed to add dark mode to the site was a dark flash when the site loaded in light mode. While the fix was straightforward (set the theme before render), the diagnosis and fix helped me understand a little more about the order of operations and how to look at invariants across time, not just at the end state.

With this workflow, both generating and running tests were quite cheap, so I decided to be generous with tests, expanding the suite with performance tests, fixtures, and other enhancements. One thing that cut down the amount of test rework was pulling out constants and magic numbers from within tests, which were fragile (e.g. depending on a test post page that was not guaranteed to be present). I've since started to invest more cycles in the test suite as well, since it does real work for me, and running the tests before each change is a frictionless reflex by now.

Last, but not least, I found that I could be more ambitious in features such as generating custom post card layouts, adding search and tagging features, and more. I found that I could step away from steering the model as I had done months before, and focusing attention on the changes that I wished could be made. Essentially, with tests, I found myself wishing for changes and getting them made, with confidence.

There are still some real limitations here. The tests don't catch what I haven't specified, and the path to surfacing that is usually through my manual work in a real browser as the key gate. I wouldn't rely on this for confidence in a system with stakes. For this blog, though, it does its job and gets out of the way.

Of course, I then took things beyond what a reasonable person would ask for, because why not.

**3. Overengineering for fun and profit**: Later on, my daily driver laptop involuntarily became a desktop, and when setting up a new one I turned to asking whether I could save the hassle of installing all my build and test dependencies on bare metal.

Jesting about overengineering aside, there were a couple of risks that I was worried about and wanted to get ahead of. The first was that when building out some features, I noticed the commentary attached to the generated responses flagging that the liquid syntax and features may rely on newer releases than what I had installed. In an ordinary project, I'd just bump the version, however github pages (which hosts this site) isn't a workflow that I control. What I needed to do was to match the build process, rather than let my setup drift away from it.

The second thing I wanted to do was put up some guard rails around the codebase. I still merge across the code myself, but I wanted to leave the door open to experiment with an agent. After getting spooked with field reports of leaked secrets and credentials, I felt like it would be helpful to guard against both an LLM running rogue and the risk that a merged test contains malicious code.

So, I wished for a containerised test environment, one matching the infrastructure I built up and approximating, as best as I can, the github pages workflow. I wanted the container to bundle ruby, python / uv, and playwright, and pave the way in case I wanted to let an agent loose on the codebase without impacting my machine.

Learning about containers was a fun exercise, after initially getting started using VMs. Working through the permutations of the build order and what isolation containers can and cannot provide took a while. This needed me to be clear about what exactly I was defending against, and why. The first threat is that the tests I'm running have malicious code, and the second layer is a potentially misbehaving agent.

Based on this, I could reject a few things pretty quickly. Using a VM or a remote EC2 instance would obviously protect my local machine from some really nasty exploits, but I didn't want to reach for them unless I had to due to complexity and overhead. However, when I dug more into docker, I found myself uncomfortable with the container escape risks and the privileged daemon. Rootless containers in podman seemed to mitigate the worst of these, so I started with this base.

The container design itself also involved a decision around what I would isolate. The host system was the obvious one, bind-mounting only the repo to ensure that a process in the container can't see any secrets to leak. However, in practice network isolation didn't fully work because I need a connection to view the page rendered by `jekyll serve` in the container. This means outward attacks are possible, especially if I let an agent loose inside the container, but this is something I'll have to catch as it happens.

The net result is a container that I've been comfortable moving across machines, replacing an `install.sh` file that could always conflict with other programs, and keeps my workflow intact through a makefile that captures the commands I need the most.

**4. Where to from here**: This exercise has been instructive in learning to build a workflow that works for me, but has also relocated the bottleneck in feature building from "when I can muster the energy" to "when I have an idea", which is perhaps the largest shift in my own personal use of LLMs over the past months.
